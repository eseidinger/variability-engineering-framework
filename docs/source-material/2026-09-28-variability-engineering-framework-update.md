# Variability Engineering Framework

> **Archived source document.** Its product and architecture direction is incorporated into the canonical documentation. When conflicts occur, the canonical product, architecture, and architecture decision record documents take precedence.

Status: product and architecture direction incorporated into the canonical documentation on September 28, 2026. Capabilities beyond the initial UI/API integration remain planned unless the repository records implementation evidence.

## Overview

The **Variability Engineering Framework** is a domain-independent framework for modeling, analyzing, exploring, visualizing, and optimizing systems with a large number of possible variants.

Many real-world systems can be described as combinations of features, options, resources, or components. Individual elements may only occur under specific conditions, and constraints may restrict which combinations are valid.

Examples include:

- menus composed of dishes and ingredients,
- configurable software systems composed of modules,
- cloud deployments composed of infrastructure resources,
- configurable products composed of components,
- service portfolios composed of capabilities,
- manufacturing or supply-chain configurations.

The framework provides a common model for these domains and tools for answering questions such as:

- Which variants exist under a given set of constraints?
- Which elements occur in which variants?
- How is the variant space structured?
- How does the structure change when analysis dimensions are reordered?
- What is the impact of adding or removing an element, feature, or constraint?
- Which resources contribute most to the available variety?
- Which subset of variants provides the highest coverage?
- How can resource usage be minimized while maintaining sufficient variety?
- Which trade-offs exist between competing optimization objectives?

The project therefore goes beyond traditional **Variability Analysis** and treats analysis as one part of a broader **Variability Engineering** approach.

# 1. Conceptual Model

The framework is based on a small set of domain-independent concepts.

## Features and Analysis Dimensions

**Features** are decision variables in a generative configuration model. **Analysis dimensions** are typed properties used to partition and filter variant records. A feature can provide a dimension, but imported attributes and documented derivations can also provide dimensions without becoming configurable features.

Depending on the domain, examples could include:

```text
Diet = Vegan
Cuisine = Italian
Season = Summer
```

or:

```text
Database = PostgreSQL
Deployment = Kubernetes
Authentication = OIDC
```

The framework can hierarchically decompose the variant space along these dimensions.

For example:

```text
Diet
├── Vegan
│   ├── Italian
│   ├── Indian
│   └── Thai
├── Vegetarian
└── Omnivore
```

The hierarchy is not fixed. Dimensions can be reordered:

```text
Cuisine
├── Italian
│   ├── Vegan
│   ├── Vegetarian
│   └── Omnivore
├── Indian
└── Thai
```

Dimensions may also be filtered, hidden, or aggregated.

This allows the same variant space to be explored from different perspectives.

## Elements

An **Element** is something whose occurrence varies between variants.

Examples include:

| Domain | Element |
|---|---|
| Food service | Ingredient |
| Software | Module |
| Cloud infrastructure | Resource |
| Product configuration | Component |
| Service portfolio | Capability |

The generic concept intentionally avoids domain-specific terminology such as *component* or *ingredient*.

The canonical core term is *element*. Domain applications remain free to display *ingredient*, *module*, *resource*, *component*, *capability*, or another appropriate term.

## Element Usages and Presence Conditions

An element usage records an element's occurrence in a variant. The initial model supports binary usage; quantities, units, cost, and other attributes require explicit later semantics.

In a generative model, an element may be associated with a **Presence Condition** describing when it occurs.

Conceptually:

```text
Presence(Element) := Boolean expression over features
```

For example:

```text
CoconutMilk :=
    Cuisine = Thai
    OR Cuisine = Indian
```

or in a software system:

```text
Redis :=
    DistributedCaching
    AND Deployment != SingleNode
```

Presence conditions connect a generative feature model with the elements that constitute a particular variant. Imported observations can instead provide element usages directly and must not be presented as generated by rules that were not in the source.

## Constraints

Not every theoretical combination of feature values represents a valid configuration.

Constraints describe relationships such as:

```text
A requires B

A excludes C

exactlyOne(A, B, C)

atLeastOne(A, B)
```

These are model constraints used to determine valid complete configurations. Numeric rules over a selected portfolio, such as a budget or minimum dietary coverage, are portfolio constraints and use a separate contract.

## Variant Records and Populations

A structural **Variant** is a normalized collection of element usages. A **Variant Record** is an identified generated or imported candidate with its structural variant, analysis dimensions, and provenance. Multiple records can have the same structural variant.

A versioned **Analysis Population** contains the records analyzed together. Generative models create records from valid complete configurations; domain adapters map observed datasets to records while preserving source, mapping, and derivation provenance. This common representation supports the same downstream analysis without conflating observed data with generative rules.

# 2. Variability Analysis

The **Variability Analysis Engine** explores the resulting variant space.

A central concept is the hierarchical decomposition of variants according to selected dimensions.

Users can:

- reorder dimensions,
- hide dimensions,
- aggregate dimension values,
- filter variants,
- compare branches,
- inspect elements associated with variants,
- calculate statistics for individual branches.

This turns the hierarchy into an interactive analytical view rather than a static taxonomy.

For example, the same data can answer:

```text
How do vegan dishes differ between cuisines?
```

and:

```text
How does the vegan share differ for each cuisine?
```

simply by changing the order and aggregation of analysis dimensions.

---

# 3. Impact Analysis

The framework can analyze how changes affect the variant space.

Typical questions include:

```text
What happens if an element becomes unavailable?

What happens if a new constraint is introduced?

Which variants depend on a particular element?

Which elements are critical for maintaining diversity?

Which parts of the variant space disappear after a change?
```

Impact analysis compares an explicit scenario with a versioned baseline. For example, element unavailability may make every record using it infeasible; silently removing the element from each record would be a different operation.

---

# 4. Configuration

While Variability Analysis examines a variant space, **Configuration** works in the opposite direction.

Given a partial assignment or supported requirements such as:

```text
Feature A = true
Feature B = false
Feature C = X
```

the configuration engine determines compatible complete configurations and their resulting variants and elements. The partial request itself is not treated as a complete configuration.

This supports applications such as product configurators, infrastructure planners, and software deployment tools. Menu planning is normally portfolio selection rather than completion of one feature configuration.

---

# 5. Variability Optimization

Many real-world variability problems involve competing objectives.

The framework therefore extends analysis with optimization capabilities.

Typical objectives include:

```text
maximize diversity

maximize feature coverage

maximize customer requirement coverage

minimize number of elements

minimize cost

minimize environmental impact

minimize operational complexity
```

Subject to constraints such as:

```text
budget <= X

at least N vegan options

all required capabilities must be covered

resource usage <= available capacity
```

Multiple objectives can be considered simultaneously.

Optimization selects a **Portfolio**, a collection of variant records from an identified candidate population. Portfolio constraints and objectives are separate from Boolean model constraints. Instead of necessarily producing one globally "best" portfolio, the system can expose **Pareto-optimal portfolios** and allow users to explore the trade-offs between objectives.

# 6. Primary Demonstration Use Case: Food Service

A restaurant or cafeteria provides an intuitive demonstration of the framework because menus naturally form a large configuration and optimization space.

## Domain Mapping

The generic model can be mapped to the food-service domain as follows:

| Framework concept | Food-service concept |
|---|---|
| Variant record | Identified recipe or dish |
| Structural variant | Normalized ingredient-usage signature |
| Element | Ingredient |
| Element usage | Ingredient occurrence, later with quantity and unit |
| Analysis dimension | Cuisine, diet, dish type, season |
| Model feature | Decision variable only where a generative recipe model defines one |
| Scenario | Ingredient unavailability or another explicit change |
| Portfolio constraint | Dietary, budget, inventory, or operational requirement over a menu |
| Portfolio | Menu offered by a restaurant or cafeteria |

Possible dimensions include:

```text
Cuisine
Diet
DishType
Season
PreparationMethod
PriceCategory
Allergens
```

Elements are primarily ingredients:

```text
Tomato
Rice
Chicken
Tofu
Coconut milk
Potato
...
```

Public recipe datasets can provide thousands of observed recipe records with ingredient lists, cuisines, dietary labels, and other attributes.

A domain adapter maps those observations into a versioned analysis population. Imported and derived values retain their provenance; the framework does not infer a generative variability model unless an explicit, validated inference process is added.

# 7. Menu Portfolio Optimization

Consider a cafeteria that wants to offer a diverse menu while keeping operational complexity low.

A central question is:

> How can we create a diverse menu using as few different ingredients as possible while covering as many dietary requirements as possible?

This is a multi-objective optimization problem.

Possible objectives are:

```text
maximize number of dishes
maximize cuisine diversity
maximize dietary coverage
minimize number of ingredients
minimize ingredient cost
```

Possible constraints include:

```text
at least 5 vegan dishes
at least 5 vegetarian dishes
at least 3 gluten-free dishes
at least 4 different cuisines
maximum 50 distinct ingredients
```

The framework could generate multiple menu portfolios representing different trade-offs.

For example:

```text
                 Ingredients   Dishes   Diet Coverage   Cuisines

Menu A                30          15          High           4
Menu B                42          25          High           7
Menu C                25          12          Medium         5
```

The user can then explore why the portfolios differ using the same variability-engineering tools.

---

# 8. Ingredient Leverage Analysis

Another question is:

> Which ingredients enable the greatest variety of dishes?

An ingredient such as tomato, onion, rice, or garlic may occur across many cuisines and dietary categories.

The framework could calculate measures such as:

```text
Ingredient
    → number of supported recipes
    → number of cuisines
    → number of dietary categories
    → number of dish categories
```

A generalized **Element Leverage** metric could express how much variability an element enables relative to its cost or operational complexity.

The same concept can later be applied to software modules, cloud resources, or product components.

---

# 9. Marginal Value Analysis

A restaurant may already have a defined inventory.

The relevant question then becomes:

> Which additional ingredient would increase the possible menu variety the most?

For example:

```text
Current inventory
        │
        ├── + Coconut milk → +23 possible dishes
        ├── + Chickpeas    → +17 possible dishes
        ├── + Eggs         → +14 possible dishes
        └── + Saffron      →  +1 possible dish
```

The inverse analysis is equally useful:

> Which ingredient can be removed with the smallest reduction in menu variety?

This represents a general **marginal value analysis** for elements.

---

# 10. Supply-Chain Impact Analysis

Ingredient availability can change because of supply-chain problems, seasonal availability, or purchasing decisions.

The framework can answer:

> What happens to our menu if a particular ingredient becomes unavailable?

For example:

```text
500 available dishes
        │
        │ remove ingredient X
        ▼
372 available dishes
```

The effect can then be decomposed:

```text
Diet
├── Vegan             -12%
├── Vegetarian        -18%
└── Omnivore           -7%

Cuisine
├── Italian           -35%
├── Indian             -4%
└── Mexican           -11%
```

This makes dependencies and vulnerabilities within the menu portfolio visible.

# 11. Dietary Requirements and Allergens

Dietary restrictions provide another natural constraint system.

Examples include:

```text
Vegan
Vegetarian
Gluten-free
Lactose-free
Nut-free
```

Questions include:

> How many dishes remain if they must be vegan and gluten-free?

> Which dietary requirements are difficult to combine?

> Which ingredients prevent otherwise suitable dishes from satisfying a requirement?

> How many ingredients are necessary to maintain meaningful coverage for every supported diet?

These analyses demonstrate how filtering and constraint propagation reduce the variant space.

---

# 12. Seasonal Menu Planning

Availability can itself become a feature.

For example:

```text
Season
├── Spring
├── Summer
├── Autumn
└── Winter
```

The system could answer:

> Which dishes can be produced entirely from seasonally available ingredients?

or:

> Which additional ingredients would increase the variety of the winter menu the most?

Seasonal availability therefore combines variability analysis, impact analysis, and optimization.

---

# 13. Cost and Sustainability

Additional datasets can enrich ingredients with properties such as:

```text
Price
CO2 footprint
Transportation distance
Storage requirements
Shelf life
```

Menu planning then becomes a more complex optimization problem:

```text
maximize diversity
maximize dietary coverage

minimize cost
minimize CO2 emissions
minimize number of ingredients
minimize storage complexity
```

There may no longer be a single optimal answer.

Instead, the framework can visualize trade-offs between different Pareto-optimal menu portfolios.

---

# 14. Multi-Site Food Service

The concept can be extended from a single restaurant to multiple cafeterias.

Each location may have different requirements while sharing purchasing and logistics.

The optimization problem becomes:

> How can multiple locations offer sufficiently different menus while sharing as much of the ingredient inventory as possible?

Conceptually:

```text
                   Shared Ingredient Portfolio
                             │
              ┌──────────────┼──────────────┐
              │              │              │
          Location A     Location B     Location C
              │              │              │
           Menu A         Menu B         Menu C
```

This introduces another level of variability and demonstrates that the framework can analyze portfolios of variant records rather than individual variants only.

# 15. Additional Use Cases

The food-service example is only one application of the generic model.

## Software Product Lines

Software systems are a natural application for variability engineering.

Features could include:

```text
Authentication
Database
Messaging
Caching
Deployment
Observability
```

Elements could be:

```text
application modules
libraries
services
containers
configuration artifacts
```

Presence conditions determine which modules are required by a particular configuration.

The framework could answer:

- Which modules are shared by most configurations?
- Which feature introduces the greatest implementation complexity?
- What is affected when a module is removed?
- Which minimal set of modules supports a required capability portfolio?

Existing Software Product Line feature-model datasets can serve as benchmarks.

# 16. Cloud and Deployment Architectures

A deployment architecture can also be treated as a configurable system.

Features might include:

```text
Availability = Standard | High
Database = PostgreSQL | MongoDB
Compute = VM | Container | Kubernetes
Cache = None | Redis
Region = EU | US
```

Elements might include:

```text
VM
Kubernetes cluster
PostgreSQL instance
Redis instance
Load balancer
Object storage
Monitoring service
```

Possible optimization questions include:

> Which architecture satisfies the requirements with the fewest infrastructure components?

> What additional infrastructure is required when high availability is enabled?

> Which configurations satisfy a given cost limit?

> How does removing a technology affect the set of possible architectures?

This use case connects variability engineering directly with architecture decision support.

# 17. Configurable Products

Traditional configurable products provide another application.

Examples include:

```text
computer systems
industrial machines
electronic devices
manufacturing equipment
```

Features describe customer-visible choices, while elements represent the physical or logical components necessary to realize them.

The framework can analyze:

- valid configurations,
- component reuse,
- configuration complexity,
- dependencies between options and components,
- impact of unavailable components,
- portfolio simplification.

Public product datasets, such as laptop specification datasets, can provide demonstration data.

---

# 18. Service and Capability Portfolios

The abstraction does not require variants to represent physical products.

A service platform could model:

```text
Variant → service offering
Element → underlying capability
Feature → customer requirement
```

This enables questions such as:

> What is the smallest capability portfolio required to provide all important service offerings?

or:

> Which capability contributes to the largest number of offerings?

This demonstrates that the underlying model applies beyond traditional product configuration.

# 19. Framework Architecture

The long-term goal is to separate the domain-independent variability model from domain-specific adapters and visualization components.

Conceptually:

```text
              Generative Models              Observed Datasets
                 │         │                         │
          Model Evaluation │                  Domain Adapters
                 │    Configuration                  │
                 │       Assistance                  │
                 │         │                         │
                 └─────────┴────────────┬────────────┘
                                       │
                          Normalized Analysis Population
                                       │
                         ┌─────────────┼─────────────┐
                         │             │             │
                      Analysis       Impact      Portfolio
                       Engine        Engine      Optimization
                         │             │             │
                         └─────────────┼─────────────┘
                                       │
                             Visualization Model
                                       │
                              UI Components / APIs
```

The core model and algorithms should remain independent of a particular application domain.

Domain adapters translate external datasets and domain terminology into normalized variant records while preserving provenance. They do not invent generative features or presence conditions.

# 20. Project Goals

The project has several complementary goals.

### Domain Independence

Demonstrate that the same variability model can represent fundamentally different domains.

### Interactive Analysis

Provide tools for exploring large variant spaces by dynamically changing dimensions, filters, aggregations, and hierarchy levels.

### Explainability

Optimization results should not only return portfolios but also make their consequences understandable through variability and impact analysis.

### Extensibility

The framework should allow new domains, analysis algorithms, optimization objectives, and visualization components to be added independently.

### Technology Independence

The conceptual model should not depend on a single programming language or frontend technology. Implementations and client libraries can therefore be provided for multiple ecosystems.

# 21. Vision

The project aims to bridge the gap between **variability modeling**, **interactive analysis**, **configuration**, and **optimization**.

Rather than treating these as isolated problems, the framework provides a common representation of a configurable system and uses it for different analytical tasks:

```text
                    Variability Engineering
                              │
          ┌───────────────────┼───────────────────┐
          │                   │                   │
       Modeling            Analysis          Optimization
          │                   │                   │
          └────────── Configuration ──────────────┘
                              │
                       Decision Support
```

The food-service scenario serves as an accessible demonstration:

> **How can a cafeteria provide a diverse menu covering different dietary requirements while minimizing the number of ingredients, cost, and operational complexity?**

The same underlying framework can then address structurally similar questions in software architecture, cloud infrastructure, configurable products, and service portfolios.

The central hypothesis of the project is that these apparently different problems share a common structure:

> **A large population of possible or observed variant records, a set of elements used by their structural variants, and the need to understand or optimize the resulting variability space.**

The Variability Engineering Framework provides a domain-independent foundation for modeling and solving this class of problems.
