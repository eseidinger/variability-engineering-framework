# Domain Model

Status: core analysis concepts are requirements; food-service analysis semantics are binding for the MVP; portfolio and quantitative-usage semantics remain documented direction requiring later contracts and conformance cases.

The bounded [energy model](energy-configuration.md) now implements quantitative
new-equipment selections and configuration generation against a separate released
contract. It does not change observed binary variant identity or establish
general-purpose quantity, recipe, or portfolio semantics.

| Term | Meaning |
|---|---|
| Feature | Variable describing a configuration. |
| Feature Domain | Permitted values of a feature. |
| Configuration | Complete assignment of values to all features in a generative model. |
| Partial Requirement | Incomplete feature assignment or supported predicate used to find compatible configurations. |
| Model Constraint | Rule determining whether a complete configuration is valid. |
| Element | Domain-neutral constituent used by a variant, such as an ingredient, module, resource, component, or capability. |
| Element Usage | Occurrence of an element in a variant; initially binary and later optionally quantitative. |
| Presence Condition | Rule determining whether an element is present. |
| Variant | Structural value defined by a normalized collection of element usages. |
| Variant Record | Identified generated or imported candidate with dimensions, provenance, and a structural variant. |
| Analysis Dimension | Feature, imported attribute, or derived classification used to partition and filter records. |
| Analysis Population | Versioned collection of variant records analyzed together. |
| Scenario | Explicit change applied to a baseline model or population for impact comparison. |
| Portfolio | Selected collection of variant records. |
| Portfolio Constraint | Rule over a portfolio, such as minimum coverage or maximum total cost. |
| Objective | Quantity to minimize or maximize when selecting a portfolio. |

`Element` is the canonical core term. Domain applications may present ingredients, modules, resources, components, or other entities in their own terminology; `Entity` is not a second core type.

## Generative models

```text
C_possible = D1 × D2 × … × Dn
C_valid    = { c in C_possible | all constraints are satisfied by c }
Variant(c) = normalize({ usage(e) | PresenceCondition(e, c) = true })
Record(c)  = identified record containing c, Variant(c), dimensions, and provenance
V_distinct = { Variant(c) | c in C_valid }
```

A complete configuration generates one record under a particular model version. Different configurations may produce structurally equal variants, so `configurationCount`, `recordCount`, and `variantCount` are different metrics. A partial requirement is input to configuration assistance, not a configuration until it has been completed and validated.

The initial binary signature compares variants as unordered sets of stable element IDs. Quantities, units, and other usage attributes require a later, versioned equality rule before they can affect structural identity.

## Observed populations

Observed datasets do not need to pretend that imported attributes are decision variables or that element membership was generated by presence conditions. A domain adapter maps each source row or object to a variant record containing:

- a stable record ID within the source version;
- imported and derived analysis-dimension values;
- normalized element usages;
- source, license, mapping-version, and derivation provenance; and
- a structural variant signature calculated with the same documented equality rule used for generated records.

Generated and observed records therefore share the downstream analysis representation while retaining their different provenance. An analysis population must not mix source or model versions without identifying the composition explicitly.

## Analysis dimensions

Features and analysis dimensions are related but not identical. A feature is a decision variable in a generative model. An analysis dimension is a typed projection available on records and may originate from a feature, imported metadata, or a documented derivation. Dimension origin and missing-value behavior are part of the contract.

## Scenarios and impact

A scenario names a baseline and a set of changes. For example, element unavailability can make every record using that element infeasible; removing the element from each variant would be a different scenario and must not happen implicitly. Impact results identify the scenario rule and compare record, distinct-variant, element, and dimension-group metrics against the baseline.

## Portfolios and optimization

A portfolio selects variant records from an identified candidate population. It is not itself a variant. Portfolio constraints and objectives operate over the selected records and their element usages; they are separate from model constraints that validate one feature configuration.

An optimization result includes the input versions, feasible portfolio, objective values, constraint evaluations, and solver status. With competing objectives, the result may contain a Pareto frontier rather than one globally best portfolio.

In the food-service mapping, a recipe or dish is a variant record, an ingredient is an element, cuisine and diet are analysis dimensions, and a menu is a portfolio.
The binding food-service analysis subset, including structural identity, dimension cardinality, missing values, version provenance, filters, metrics, and ingredient unavailability, is defined in [Food-Service Analysis MVP Semantics](food-service-mvp-semantics.md). Later quantity, portfolio, and optimization semantics must not be inferred from that MVP contract.



Features are `region = EU | US`, `advanced = false | true`, and `theme = light | dark`. Elements are `base: true`, `reporting: advanced`, and `euPolicy: region = EU`. With no constraints, the fixture has eight valid configurations, eight generated records, and four distinct variants. Adding `NOT (region = US AND advanced = true)` produces six valid configurations, six generated records, and three distinct variants.

Initial proposals limit feature types to Boolean and finite enumerations, require complete assignments for evaluation, reject unknown feature references before evaluation, and use binary element presence. Numeric quantities, portfolio expressions, and optimization objectives are outside the initial portable Boolean expression contract.
